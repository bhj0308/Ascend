# /migrate "<message>"

Alembic autogenerate is a starting point, not a finished migration. Every migration here is
proven to round-trip before it is considered done.

## 1. Generate
```bash
cd backend && source venv/bin/activate
alembic revision --autogenerate -m "<message>"
```
Open the new file in `migrations/versions/`. Read the whole thing.

## 2. Fix what autogenerate gets wrong
- **Enum types are not dropped on downgrade.** For every `sa.Enum(..., name='<x>')` that this
  migration *creates*, append to the end of `downgrade()`:
  `op.execute("DROP TYPE IF EXISTS <x>")`
  Do this only for enums this migration introduces — not ones that already existed.
- Column renames appear as drop+add (data loss). If a rename was intended, replace with
  `op.alter_column(..., new_column_name=...)`.
- Adding a `NOT NULL` column to a table with rows needs a `server_default` or a data step.
- Enum *value* changes on Postgres need `ALTER TYPE ... ADD VALUE` (cannot run inside a
  transaction — use `op.get_bind().execute(text(...))` with `autocommit`) or a type swap.

## 3. Prove the round-trip
```bash
alembic upgrade head
alembic downgrade -1          # or `base` for an initial migration
psql "$DATABASE_URL" -tAc "SELECT typname FROM pg_type WHERE typtype='e'"   # new enums must be gone
alembic upgrade head
alembic current               # must show the new revision (head)
```
If any step errors, fix the migration file — do not hand-edit the database to get past it.

## 4. Report
- Revision id and message
- Tables/columns/enums added, changed, dropped
- Round-trip result (paste the `alembic current` line and the enum query output)
- Any manual edits you made to the autogenerated file and why
